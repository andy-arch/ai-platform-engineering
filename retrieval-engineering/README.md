# Retrieval Engineering — Phase 2

A local, dependency-light retrieval pipeline: documents in, embeddings and
a vector index out, ranked chunks back for a query. This is the layer
that a future RAG pipeline (Phase 3) will sit on top of — an LLM call is
deliberately *not* part of this phase. The goal here is to understand and
demonstrate retrieval mechanics before hiding them behind a framework or
a managed vector database.

Builds directly on [`foundations/embedding`](../foundations/embedding)
(Phase 1) — reuses its `EmbeddingProvider` abstraction rather than
reimplementing embedding logic.

```
documents -> ingestion -> chunking -> metadata -> embeddings -> vector store -> retrieval -> top-k chunks
```

## Setup

This package is installed as part of the repo-root `pyproject.toml`, so
`retrieval_engineering.*` and `foundations_embedding.*` can be imported
with plain absolute imports from anywhere in the venv — no `sys.path`
tricks needed.

```bash
# from the repo root
python -m venv .venv
.venv\Scripts\activate        # on Windows; source .venv/bin/activate on macOS/Linux
pip install -e .
pip install -r retrieval-engineering/requirements.txt
```

You don't need `sentence-transformers` or an API key to run anything —
it falls back to Phase 1's offline hash-based provider, same as Phase 1.
Install `sentence-transformers` (already required by
`foundations/embedding`) to get real semantic embeddings.

## Usage

```bash
# 1. build the index from data/knowledge
python retrieval-engineering/scripts/ingest.py

# 2. query it
python retrieval-engineering/scripts/search.py "How does EKS authentication work?"

# 3. evaluate retrieval quality against the labeled question set
python retrieval-engineering/scripts/evaluate.py

# 4. run the tests (offline, deterministic)
pytest retrieval-engineering/tests -v
```

## 1. What is Retrieval Engineering?

Retrieval engineering is the discipline of getting the *right* pieces of
text in front of a model (or a human) for a given query, out of a corpus
too large to hand the model in full. It sits between "raw documents" and
"an LLM call": ingest and structure content once, then answer many
queries against it cheaply. Everything in this module —
ingestion, chunking, metadata, embeddings, vector storage, ranking — is
in service of that one operation: `query -> top_k relevant chunks`.

## 2. Why embeddings alone are not enough

Phase 1 showed that an embedding model can turn text into a vector where
geometric closeness approximates semantic closeness. That's necessary
but not sufficient for retrieval over a real knowledge base:

- **You need something to embed.** A raw document isn't a good unit to
  embed and retrieve — it's too coarse (see Chunking below).
- **You need to know where a result came from.** A similarity score
  alone is useless without the source, category, and surrounding
  context — that's what Metadata is for.
- **You need somewhere to put the vectors.** Comparing a query against
  every embedding requires storing them efficiently and searching them —
  that's the Vector Store.
- **You need a way to know if it's actually working.** A retrieval
  system can look reasonable and still perform badly — that's why
  Evaluation (Recall@K, MRR) exists as a distinct step, not an
  afterthought.

Embeddings are the mechanism; retrieval engineering is the system built
around them.

## 3. Document ingestion pipeline

`ingestion/loader.py` discovers `.md`/`.txt` files under a knowledge
root and loads each into a `Document` (id, source path, filename,
document type, raw content, metadata). It's deliberately generic — it
has no idea what "aws" or "kubernetes" means; it just walks a directory
and reads files. That genericness is what makes it reusable for an
arbitrary knowledge base, not just the sample one in `data/knowledge`.

Document ids are derived deterministically from the source path (a
SHA-256 hash, truncated), so re-ingesting the same file structure
produces the same ids rather than random ones each run.

## 4. Chunking

A whole document is usually the wrong unit to embed and retrieve:

- **Too large, and relevance gets diluted.** A 2,000-word document about
  EKS that mentions IAM once in passing will score moderately similar to
  an IAM query even though only one sentence is actually relevant — and
  if retrieved, a downstream generation step has to read the whole thing
  to find that one sentence.
- **Too small, and you lose context.** A single sentence pulled out of a
  paragraph may be ambiguous or misleading without what came before/after
  it.

`ingestion/chunker.py`'s `FixedSizeChunker` splits on a configurable
character `chunk_size`, trying to break on whitespace rather than
mid-word, with a configurable `overlap` so content near a chunk boundary
isn't orphaned into just one chunk. Trade-offs:

| | Small chunks | Large chunks |
|---|---|---|
| Precision | Higher — less irrelevant text per hit | Lower — more irrelevant text per hit |
| Context | Can lose surrounding context | Preserves more context |
| Storage / index size | More vectors to store and search | Fewer vectors |
| Embedding cost | More embedding calls | Fewer embedding calls |

Overlap trades a bit of extra storage/embedding cost for not losing a
concept that straddles a chunk boundary. Chunk ids are content-addressable
(a hash of document id + chunk index + text), so they're deterministic
across runs and change automatically if the underlying content changes.

`ChunkingStrategy` is a `Protocol`, so a token-aware or
structure-aware (e.g. split-on-heading) strategy can be added later
without touching `chunk_documents()` or any caller.

## 5. Metadata

`ingestion/metadata.py` derives `category` (top-level directory),
`topic` (filename stem), `document_type`, and — for Markdown — `title`
(the first H1) from the document's path and content, rather than
requiring metadata to be hand-maintained per file. Every chunk inherits
its parent document's metadata.

Metadata matters more as a knowledge base grows: with 12 documents,
brute-force search over everything is instant either way. At scale, you
want to narrow the search space first (e.g. "only search `category=aws`")
both for relevance (a Kubernetes query has no business matching an AWS
IAM chunk) and for cost (searching 10,000 vectors instead of 10,000,000).
`vector_store/local_store.py`'s `search(..., filters={...})` and
`retrieval/semantic_retriever.py`'s `retrieve(..., filters={...})`
support exact-match metadata filtering today; this is also the hook
point for hybrid (keyword + vector) search later.

## 6. Vector storage

A "vector database" is, underneath, three things: a matrix of vectors,
a way to compare a query vector against every row of that matrix, and a
way to persist and reload both the matrix and the payload (text,
metadata) associated with each row. `vector_store/local_store.py` is
exactly that, using NumPy for the matrix and `top_k_similar()` (Phase
1's `similarity.py`) for the comparison.

It persists as two files rather than one — `<name>.vectors.npy` for the
raw float matrix, `<name>.payload.json` for chunk text/ids/metadata,
row-aligned by index. Real vector databases separate vector data from
payload for the same reason: vectors are dense binary data best handled
by a format built for arrays, while payload is small, structured, and
worth keeping human-inspectable.

A managed vector database (Pinecone, Weaviate, pgvector, OpenSearch,
etc.) replaces this module's *implementation* — approximate nearest
neighbor indexing instead of brute force, distributed storage, built-in
filtering at scale — without needing to change `add()`/`search()`'s
*interface*, which is the point of keeping it behind an abstraction.

## 7. Semantic retrieval

`retrieval/semantic_retriever.py` implements: embed the query with the
same provider used at ingestion time, compare that vector against every
stored vector (or every vector matching the metadata filter), and return
the highest-scoring chunks.

**Cosine similarity** (the default metric, inherited from Phase 1) is
the cosine of the angle between two vectors — it measures *direction*,
not magnitude. For text embeddings this matters because a vector's
magnitude often just reflects how much text went into producing it, not
how relevant it is; two chunks about the same topic should score highly
similar whether one is a sentence and the other a paragraph, and cosine
similarity is invariant to that difference in length-driven magnitude.

## 8. Top-K retrieval

Retrieval returns the K highest-scoring chunks, not "everything above
some threshold" — similarity scores from different queries aren't
comparable on an absolute scale, so a fixed threshold is fragile in a way
a fixed K isn't. But K itself is a real trade-off:

- **Too few (K=1–2):** if the single best-scoring chunk isn't quite the
  right one, there's nothing to fall back on, and a downstream generation
  step has very little context to work with.
- **Too many (K=20+):** dilutes a downstream model's context with
  marginally-relevant chunks, costs more tokens/latency if this feeds an
  LLM, and can bury the one genuinely relevant chunk among noise.

This module defaults to K=5 and exposes it as a parameter everywhere
(`retrieve(..., top_k=...)`) rather than hardcoding it, since the right
value depends on chunk size, corpus size, and what consumes the results.

## 9. Retrieval evaluation

`evaluation/metrics.py` implements two standard retrieval metrics,
computed against `evaluation/retrieval_questions.json` (12 hand-written
questions, one per knowledge base document, each labeled with its
expected source file):

- **Recall@K** — for one question, 1.0 if any expected source appears
  among the top-K results, else 0.0; averaged across questions. Answers
  "what fraction of the time is a relevant document found within the
  first K results?" It doesn't care *where* within the top K a good
  result landed, only whether it's there at all.
- **MRR (Mean Reciprocal Rank)** — for one question, `1 / rank` of the
  first result whose source is expected (0 if none of the retrieved
  results match); averaged across questions. Unlike Recall@K, MRR
  rewards ranking the right answer *higher*: rank 1 scores 1.0, rank 2
  scores 0.5, rank 5 scores 0.2.

Run `python scripts/evaluate.py` to compute both against the current
index. This is intentionally simple — exact source-file matching, no
partial credit, no relevance grading — a baseline to build on, not a
finished evaluation framework.

## 10. Current limitations

This implementation deliberately does **not** solve:

- **Hybrid search.** No keyword/BM25 component — purely dense vector
  similarity, which struggles with exact identifiers, acronyms, and
  rare terms that a lexical match would catch easily.
- **Reranking.** No second-stage cross-encoder or LLM-based reranker to
  refine the initial top-K before it's used downstream.
- **A distributed or approximate-nearest-neighbor vector database.**
  Search here is O(n) brute force in memory — fine for thousands of
  chunks, not for millions.
- **Filtering at large scale.** Metadata filtering here is a linear scan
  over the store, not an indexed filter — it's a correctness
  demonstration, not a performance one.
- **Query rewriting / expansion.** The user's query is embedded exactly
  as typed; no query decomposition, HyDE, or multi-query expansion.
- **Production observability.** No latency/quality metrics, tracing, or
  logging aggregation beyond basic Python `logging` calls.
- **Document updates/deletion at the ingestion level.** `ingest.py`
  rebuilds the index from scratch; there's no incremental
  upsert/delete-by-document flow yet (the vector store's `add()` does
  reject duplicate chunk ids, but nothing removes stale ones).
- **Generation.** No LLM is called anywhere in this phase — that's
  explicitly Phase 3.

## 11. Future evolution

```
Retrieval (this phase)
  -> Advanced RAG            (generation on top of these chunks; hybrid
                               search; reranking; query rewriting)
  -> Agentic RAG              (retrieval as a tool the agent decides
                               when and how to call, not a fixed pipeline
                               step)
  -> Tool-using agents        (retrieval alongside other tools: code
                               execution, external APIs)
  -> Multi-agent platform      (retrieval as shared infrastructure behind
                               MCP, used by many agents/roles)
```

Everything in this module is written to make that path additive rather
than a rewrite: `EmbeddingProvider` and `ChunkingStrategy` are already
swappable abstractions, and `LocalVectorStore`'s `add()`/`search()`
interface is what a managed vector database would need to implement to
be a drop-in replacement.

## Production gaps

What would need to change to run this in production, beyond the
"Current limitations" above:

- Swap `LocalVectorStore` for a managed/distributed vector database —
  the interface is designed to make this a small change, not a rewrite.
- Move from a full-rebuild `ingest.py` to an incremental
  ingestion pipeline (detect new/changed/deleted files, upsert only
  those).
- Add authentication/authorization on top of metadata filtering, if the
  knowledge base contains access-controlled content — today's filters
  are for relevance, not security.
- Add real observability: retrieval latency, score distributions, cache
  hit rates, and a way to detect quality regressions over time (not just
  the fixed 12-question evaluation set here).
- Expand the evaluation set significantly and consider graded relevance
  (not just single-expected-source) as the knowledge base grows past
  "one obvious right answer per question."
